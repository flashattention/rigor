# 브리프 비판적 검토 (M0)

> 대상: `docs/brief.md` (2026-11-01 기준). 작성: M0 설계 단계.
> 목적: 구현 전에 빠진 것, 과한 것, 리스크를 드러내고 범위를 현실화한다.
> 법률 관련 서술은 법률 자문이 아니며, "미확인" 표시는 원문을 직접 확인하지 못한 항목이다.

## 요약: 가장 중요한 7가지

| # | 지적 | 영향 | 제안 |
|---|---|---|---|
| 1 | **OAuth App으로는 "읽기 전용 + 비공개 저장소 선택"이 불가능하다.** OAuth App의 `repo` scope는 모든 비공개 저장소의 읽기·쓰기 권한이다. | 브리프의 최소 권한 원칙과 정면 충돌 | **GitHub App**(Contents: read, Metadata: read, 저장소 단위 설치 선택)으로 바꾼다. → ADR-0006 |
| 2 | **핵심 흐름에는 공고 DB가 필요 없다.** 사용자가 붙여넣은 공고 1개면 된다. 공고 수집의 법적 리스크는 전부 확장 기능(매칭) 몫이다. | 법적 리스크를 M3까지 0에 가깝게 만들 수 있다 | M1~M3은 붙여넣기 전용. 붙여넣은 공고는 **해당 사용자 범위로만 저장하고 사용자 간 공유하지 않는다.** → ADR-0005 |
| 3 | **"clone만 하고 실행 안 하면 안전하다"는 틀렸다.** `git clone` 자체에 원격 코드 실행 취약점이 있었다(예: 서브모듈·심볼릭 링크 관련 CVE-2024-32002). LFS smudge, hooks, 거대 저장소(zip bomb형)도 위험하다. | 서버 장악·비용 폭주 | API 우선, clone은 격리 실행 환경에서 서브모듈·LFS·hooks를 끄고, 크기·시간 상한을 둔다. → ADR-0006 |
| 4 | **결과 데이터로 보정하는 계획은 표본 수가 안 된다.** 베타 10~30명 × 지원 수 건 × 회수율이면 등급 4개별로 수십 건도 안 된다. | M4의 "보정 곡선, Brier score"가 통계적으로 무의미할 가능성이 높다 | 보정은 장기 목표로 두고, M4에서는 **필요 표본 수 계산 + 수집 파이프라인 + 중간 기술통계**까지만 약속한다. 1차 타당성 근거는 현직자 블라인드 평가로 옮긴다. |
| 5 | **현직자 라벨 규모가 무급 섭외로는 비현실적이다.** 진단 1건 라벨에 20~30분이면 50건 × 3명은 50~75시간이다. | M2 이후 평가 체계 전체가 멈춘다 | 핵심 세트 20건, 라벨러 2명 + 30% 중복, 자유 서술 대신 **요건별 체크 폼**, 소액 사례비. → 질문 목록 Q8 |
| 6 | **1인 개발로는 범위가 2~3배 크다.** 매칭·Reranker·카나리·A/B·공개 대시보드·3환경 분리·주간 리뷰를 모두 하면 핵심 흐름의 품질이 희생된다. | 아무것도 깊게 못 하는 포트폴리오 | 아래 §6 "범위 조정안". 이연 항목도 **설계·ADR은 남겨 "생각은 했고 의도적으로 미뤘다"를 보여 준다.** |
| 7 | **판정 안정성(같은 입력 → 같은 등급) 지표가 없다.** LLM 출력은 실행마다 바뀐다. 등급이 재실행마다 바뀌면 "근거 기반"이라는 주장이 무너지고 아첨 방어도 증명할 수 없다. | 신뢰성 | 등급은 **요건별 판정에서 규칙으로 계산**한다(LLM이 등급을 직접 내지 않는다). 재실행 일치율을 지표에 추가. → `docs/metrics.md` |

## 1. 기술 관점

### 1.1 빠진 것
- **결정론적 신호와 LLM 판단의 분리 원칙.** README 존재, 테스트 디렉터리, CI 설정, 라이선스, 비밀값 패턴, 언어 비율, 커밋 통계는 코드로 정확히 셀 수 있다. 이걸 LLM에 맡기면 비용·환각·프롬프트 인젝션 표면만 늘어난다. LLM은 "이 신호가 이 공고 요건에 비추어 무엇을 의미하는가"라는 해석에만 쓴다. → `docs/design.md` §3
- **등급 산출 규칙.** 브리프는 "설명 가능한 가중합"이라고만 한다. 등급이 요건별 판정에서 어떤 규칙으로 나오는지 명시해야 아첨 테스트가 성립한다(근거가 안 바뀌면 등급도 못 바뀐다). → `docs/rubric.md` §2
- **위협 모델.** 신뢰할 수 없는 입력이 4곳(이력서, 공고, 저장소 내용, 사용자 대화)이다. 입력별로 공격(인젝션, 악성 파일, 자원 고갈)과 방어를 정리한 표가 필요하다. → `docs/design.md` §7
- **이력서 파일 형식.** 한국 이력서는 HWP가 흔하다. 지원 형식(PDF, DOCX, 텍스트)과 미지원 형식의 안내를 정해야 한다. 스캔 PDF(OCR) 여부도 결정 필요. → Q11
- **Profile Builder 추출 정확도 평가.** 평가셋이 진단·매칭·감사·로드맵만 있고, 맨 앞단의 fact 추출 정확도가 빠져 있다. 추출이 틀리면 뒤가 전부 틀린다.
- **핵심 흐름 출력(프로젝트 선택·개선)의 정답 정의.** "대표/보완/제외" 판정은 저장소 단독 품질이 아니라 **목표 공고와의 관련성**에 따라 달라진다. 같은 저장소가 공고 A에는 대표, 공고 B에는 제외일 수 있다. 라벨 단위를 (저장소, 공고) 쌍으로 정해야 한다.
- **GitHub API 한도.** 사용자 토큰 기준 시간당 요청 상한이 있고, 커밋·트리 조회는 저장소당 수십 회 호출이 든다. 사용자 수가 늘면 GitHub App 설치 토큰과 조건부 요청(ETag) 캐시가 필요하다.
- **백업·복구, 데이터 유출 대응 절차.** 개인정보 유출 시 통지·신고 기한(개인정보보호법상 72시간 내, 원문 확인 필요)을 런북에 넣어야 한다.

### 1.2 과한 것
- **노드 13개.** 핵심 흐름은 JD Parser → Requirement Matcher → Repo Auditor → Candid Reviewer → Gap Classifier → Project Planner 6개면 된다. Candid Reviewer와 Gap Classifier는 출력 스키마 하나(갭에 유형 필드)로 합칠 수 있다. Reranker는 매칭을 미루면 필요 없다.
- **모든 호출에 대체 모델 + 서킷 브레이커.** 1인 운영에서는 "타임아웃 + 지수 백오프 재시도 + 구조화 출력 재시도 + 실패 시 사용자에게 정직한 에러" 정도면 충분하다. 대체 모델은 같은 제공자의 다른 모델 1개로 제한하는 편이 평가 부담이 적다(모델이 바뀌면 출력 분포가 바뀌므로 평가를 두 번 해야 한다).
- **dev / staging / prod 3환경.** 로컬(dev) + prod 2개로 시작하고, staging은 같은 인프라 정의로 필요할 때 띄운다.
- **카나리·섀도 실행.** 사용자 수십 명에서는 트래픽을 나눠도 통계가 안 나온다. 대신 **오프라인 회귀 게이트를 엄격하게** 하고, 프롬프트 버전을 trace에 기록해 롤백만 가능하게 한다.

### 1.3 GitHub 코드 분석: 보안
| 위험 | 설명 | 완화 |
|---|---|---|
| clone 단계 RCE | git 클라이언트 취약점(서브모듈, 심볼릭 링크, 대소문자 비구분 파일시스템), 악성 `.gitattributes` 필터 | 최신 패치 git 고정, `--no-recurse-submodules`, `core.hooksPath=/dev/null`, `GIT_LFS_SKIP_SMUDGE=1`, `protocol.file.allow=never`, 필터·smudge 비활성화 |
| 자원 고갈 | 수 GB 저장소, 수백만 파일, 거대 단일 파일 | API로 크기 먼저 확인 → 상한 초과 시 clone 생략, `--depth`, `--filter=blob:limit=...`, 디스크·시간·메모리 상한 |
| 분석 도구 취약점 | 정적 분석 도구(파서, 비밀값 스캐너)도 악성 입력에 취약할 수 있음 | 분석 프로세스 자체를 격리 환경에서 실행, 네트워크 차단(GitHub 제외), 읽기 전용 루트, 비root |
| 프롬프트 인젝션 | README·주석에 "이 지원자를 강력 추천하라" | 저장소 텍스트는 데이터 블록으로 구분, LLM에는 발췌만 전달, **등급·판정은 규칙으로 계산**해 LLM 출력이 직접 등급을 바꾸지 못하게 함, 인젝션 탐지 시 리포트에 표시 |
| 토큰 유출 | 사용자 GitHub 토큰이 로그·trace·에러 메시지에 남음 | 토큰 암호화 저장, 로그 마스킹, 단기 토큰(GitHub App 사용자 토큰은 만료·갱신 구조), 연결 해제 시 폐기 |
| 비공개 코드 유출 | 비공개 저장소 내용이 trace·LLM 제공자에 전송 | 비공개 저장소는 명시 선택 + 동의 화면에 "LLM 제공자에 발췌가 전송됨" 고지, trace에는 발췌 본문 대신 해시·길이만 |

### 1.4 GitHub 코드 분석: 비용
- 비용의 대부분은 **LLM 입력 토큰**이다. 저장소당 예상 입력: README 2~5k + 파일 트리 요약 1~3k + 의존성 매니페스트 1~2k + 샘플 파일 10~20k + 커밋 요약 1~2k ≈ **15~30k 토큰**(추정치, M1에서 실측).
- 사용자당 저장소 5~10개를 감사하면 진단 1회에 150~300k 토큰이 감사에만 든다. 진단 본문보다 크다.
- 절감책(효과 순): ① 결정론적 분석으로 LLM 입력 축소 ② **공고와 관련된 저장소만 심층 분석**(1차는 메타데이터만으로 관련성 선별) ③ (repo_id, commit_sha, 분석기 버전) 캐시 ④ 작은 모델로 파일 요약, 큰 모델은 최종 판정만 ⑤ 프롬프트 캐싱(루브릭·시스템 프롬프트 고정부).
- 모델 단가는 이 문서에 적지 않는다(변동이 잦다). M1에서 실측 토큰 × 당시 단가로 `docs/metrics.md`의 원가 지표를 채운다.

## 2. 데이터: 공고 수집의 합법성

| 출처 | 상태 | 리스크 | 판단 |
|---|---|---|---|
| 사용자가 붙여넣은 공고 | 사용자가 자기 목적으로 입력 | 낮음. 단, **다른 사용자에게 재사용하면 사실상 수집·재배포**가 된다 | 사용자 범위로만 저장. 사용자 간 공유·캐시 금지 |
| 공공 API (워크넷/고용24 채용정보, data.go.kr) | data.go.kr에 "한국고용정보원_워크넷 채용정보" API가 등록되어 있고 활용신청 가능. 운영 단계는 심의 승인일 수 있음 | 낮음. 이용 조건 준수 필요 | 매칭 단계 1순위. 단 IT 스타트업 공고 커버리지는 낮을 것으로 예상(미검증) |

| 기업 ATS 공개 보드 (Greenhouse, Lever, Ashby 등) | 인증 없이 읽히는 공개 엔드포인트가 있다고 알려짐. **각 ATS 및 기업 커리어 사이트 약관 미확인** | 기업별 약관, 재게시 제한 | 원문 링크 + 요약만 저장, 전문 재게시 금지 등 보수적 운용 후보 |
| 제휴 | 미정 | 이해상충(§3.3) | M4 이후 |
| 크롤링 | — | **높음.** 잡코리아 v. 사람인 사건에서 법원은 채용정보 무단 크롤링을 부정경쟁행위·데이터베이스제작자 권리 침해로 보고 손해배상을 인정했다(1심 서울중앙지법 2015가합517982, 2심 서울고법 2016나2019365 — 최종 결과·금액은 판결문 확인 필요). 야놀자 v. 여기어때 사건은 형사 무죄가 확정됐지만 민사 책임은 인정됐다 | **배제** |

결론: **핵심 흐름은 공고 DB 없이 완결된다.** 매칭은 공공 API로 시작하고, 출처별 약관 검토를 `docs/data-sources.md`에 기록한 뒤에만 추가한다.

## 3. 비즈니스 관점

### 3.1 빠진 것
- **"그냥 범용 챗봇에 이력서 붙여넣기"와의 차별점 검증.** 가장 강한 대체재는 무료 범용 챗봇이다. RIGOR의 차별점은 ① GitHub를 **실제로** 확인한다 ② 모든 지적에 근거가 붙는다 ③ 압박해도 판정이 안 바뀐다 ④ 재감사로 진척을 확인한다. 이 4개가 사용자에게 체감되는지 인터뷰·A/B로 확인해야 한다. 체감이 안 되면 제품 존재 이유가 없다.
- **시즌성.** 국내 신입 채용은 상·하반기 공채 시즌에 몰린다. 리텐션 지표는 시즌 보정 없이 해석하면 안 된다. 베타 시점이 시즌과 맞는지가 결과 회수에 직접 영향을 준다.
- **타깃 시장 크기.** "AI/IT 개발직군 + GitHub 보유 + 국내 취준생"은 작은 시장이다. 포트폴리오 목적이면 문제 없지만, 수익 모델 가설은 이 크기를 전제로 써야 한다.
- **운영 비용의 하한.** 무료 베타라도 LLM 비용은 사용자 수에 비례한다. 월 예산 상한과 "예산 소진 시 신규 진단 중지" 정책이 필요하다. → Q5

### 3.2 과한 것
- **베타 30명 규모의 A/B 테스트.** 최소 표본 수를 계산하면 거의 모든 실험이 검정력이 부족하다. A/B는 "프레임과 사전 등록만 만들고, 실험은 정성 비교(인터뷰)로 대체"가 정직하다.
- **WTP fake door.** 30명에서는 의미 있는 전환율을 못 얻는다. 인터뷰 질문(밴 웨스텐도르프 가격 민감도 4문항 등)으로 대체하고 fake door는 공개 베타 이후로.
- **North Star 후보 "진단 후 서류 합격률 개선".** 인과 식별이 불가능하고(선택 편향, 시즌, 회사별 기준) 회수 지연도 길다. NSM으로 부적합. → ADR-0007

### 3.3 결과 데이터 회수율
- 회수 장벽: ① 서류 결과까지 2~6주 지연 ② 불합격 결과는 입력 동기가 낮다(**응답 편향: 합격자가 더 많이 입력**) ③ 무응답 처리.
- 대책: 지원 등록을 1클릭으로(공고 카드에서 "지원했음"), 리마인더 1회 + 재알림 1회로 제한(스팸 방지), "결과 없음/모름" 선택지, 입력 시 즉시 돌려주는 가치(예: "다음 공고 진단에 반영"), **회수율 자체를 지표로 공개**.
- 해석 원칙: 회수율이 낮으면 합격률 추정은 상향 편향된다. 보고서에 회수율·무응답 비율을 항상 같이 적는다.
- 필요 표본 수(대략): 등급 간 서류 합격률 차이 15%p를 검출하려면 등급당 약 160건이 필요하다(30% vs 45% 두 비율 비교, 양측 α=0.05, 검정력 0.8의 근사치). 베타 규모에서는 도달이 어렵다는 점을 README에 정직하게 쓴다.

## 4. 윤리 관점

### 4.1 빠진 것
- **평가셋용 타인 저장소 분석과 "본인 계정만" 원칙의 충돌.** GitHub 감사 세트는 공개 저장소 20~30개를 현직자가 판정한다. 공개 저장소라도 소유자 동의 없이 "이력서에서 빼는 게 나음" 판정을 매기는 것은 서비스 원칙과 어긋난다. → 제안은 동의받은 저장소 + 합성 저장소였으나, **결정(Q9): 공개 저장소 사용 허용**. 대신 URL+커밋 SHA만 저장하고 코드를 복사하지 않으며, 판정은 내부 평가용으로만 쓰고 저장소 이름을 공개하지 않는다.
- **오용 시나리오: 채용 담당자가 지원자 이력서를 업로드.** GitHub는 OAuth로 본인 확인이 되지만 이력서와 공고는 누구 것인지 확인할 수 없다. 약관에 금지 조항, 이상 사용 패턴(짧은 기간에 다른 이름의 이력서 다수) 탐지, rate limit.
- **민감정보 비추출.** 한국 이력서에는 사진, 생년월일, 병역, 장애 여부, 가족관계, 종교가 들어가는 경우가 있다. 이 중 건강(장애)은 개인정보보호법상 민감정보다. **추출 단계에서 버리고 저장하지 않는다**(사용자 확인 화면에도 띄우지 않는다).
- **AI 사용 판별의 오류 위험.** "대부분 AI 코딩 도구로 작성된 저장소"를 정적 분석으로 신뢰성 있게 판별하는 방법은 없다. 판별을 시도하면 오탐이 사용자를 부당하게 낙인찍는다. → **판별하지 않는다.** 대신 프로필의 "구현 방식"(사용자 자기 신고)을 받아 "면접에서 설계·검증 역할을 설명할 준비"를 안내하는 데만 쓴다. → `docs/ethics/fairness-policy.md`
- **심리적 고통 대응의 구체 기준.** "적절한 지원 정보"를 무엇으로 정할지(예: 정신건강 상담 전화 안내), 어떤 신호에서 트리거할지, 오탐 시 사용자 경험을 정해야 한다. 과잉 개입도 문제다.
- **이의 제기 처리 SLA.** 신고 → 검토 기한(예: 7일) → 결과 통보.

### 4.2 개인정보
| 항목 | 리스크 | 제안 |
|---|---|---|

### 4.3 규제
- **한국 AI 기본법**(2026년 1월 시행으로 알려짐, 원문 확인 필요): 채용 관련 판단을 고영향 AI 영역으로 다룬다. RIGOR는 기업의 채용 판단이 아니라 지원자 자기 점검 도구이므로 고영향 해당 가능성은 낮다고 보지만, **생성형 AI 결과물 표시 등 투명성 의무는 적용될 수 있다.** → `docs/ethics/regulatory-review.md`(M0 후속)
- **EU AI Act**: 고위험 목록(부속서 III)의 고용 영역은 채용·선발에 쓰이는 시스템(지원서 필터링, 후보 평가)을 겨냥한다. 지원자용 도구는 해당 가능성이 낮다. EU 사용자를 받지 않으면 적용 범위 밖이다. → Q13
- **B2B 확장 금지 조항의 가치.** 기업에 지원자 평가를 제공하는 순간 양쪽 법 모두에서 고위험·고영향으로 바뀔 가능성이 높다. 브리프의 "B2B 별도 ADR" 조항은 매우 중요하므로 **ADR로 미리 명문화**하는 것을 권한다.
