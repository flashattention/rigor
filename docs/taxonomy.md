직무 메모 (판정 기준으로 쓰기 전 현직자 검토 필요):
- **Agent Engineer**: LLM을 부품으로 쓰는 다단계 시스템을 만들고 **평가로 품질을 증명**하는 직무. "프롬프트 몇 개로 챗봇"은 C01만 충족.
- **FDE (Forward Deployed Engineer)**: 고객 현장 문제를 풀어 배포까지 가는 직무. 기술 폭 + C11·C12가 핵심. 고객/사용자 실사용 근거가 없으면 치명적 갭 후보.
- **AI Engineer**: 회사마다 정의 편차가 가장 크다. 공고 본문 기반 투영의 신뢰도를 낮게 두고, 공고 요건을 우선한다.
- **ML Engineer**: 모델 학습·평가가 중심. LLM API 사용 경험만으로는 C05 미충족.
- **MLOps**: 서빙·파이프라인·모니터링. 학습 자체보다 운영.
- **Data Engineer**: 파이프라인·모델링·품질. "AI 프로젝트" 경력이 실제로는 데이터 엔지니어링인 경우가 많다 → 방향 전환 제안의 대표 사례.
- **Backend**: API·DB·운영 품질.

## 3. 숙련 깊이 (Depth) — 근거의 강도

| 깊이 | 정의 | 근거 예 |
|---|---|---|
| 0 | 언급만 | 이력서 기술 목록, 근거 링크 없음 |
| 1 | 학습·튜토리얼 | 강의·튜토리얼 따라 하기 저장소, 짧은 커밋 이력 |
| 2 | 실제 문제에 적용 | 자기 문제 정의 + 설계 + 구현 + README에 결과 |
| 3 | 운영·측정 | 실사용자·배포·평가 지표·장애 대응 등 운영 흔적 |

판정 규칙과의 연결: 요건의 `min_depth`가 없으면 `required`는 깊이 2, `preferred`는 깊이 1을 기본값으로 본다. 근거 깊이가 요건보다 1 낮으면 `partial`, 2 이상 낮으면 `unmet`.

## 4. 기술(Skill) 정규화
`SkillId`는 소문자 정규 이름 + 별칭 목록으로 관리(`langgraph` ← "LangGraph", "랭그래프"). 기술 → 역량 매핑(예: `langgraph → C02`, `pgvector → C03, C08`). M1에서 상위 200개 기술로 시작하고, 매핑 없는 기술은 `unmapped`로 기록해 주기적으로 추가.

## 5. 검토 절차
1. 현직자 2명 이상이 §2 표와 직무 메모에 의견 → 차이는 토론 후 결정, 이력을 이 문서 하단에 기록.
2. 변경 시 `taxonomy_version` 증가 → 평가 재실행.
