# ADR-0001: 백엔드 프레임워크

- 상태: 제안됨
- 날짜: 2026-11-01
- 관련: ADR-0002(에이전트 프레임워크), ADR-0004(배포)

## 배경
API 서버는 인증·업로드 검증·작업 생성·SSE 진행 스트리밍·결과 조회를 담당한다. 그래프 실행은 워커에서 하므로 API 자체는 얇다. 다만 에이전트 생태계(LangGraph, LLM SDK, 평가 도구)가 Python 중심이라 **API와 워커가 같은 언어·같은 스키마(Pydantic)를 공유**하는지가 1인 개발 생산성을 크게 좌우한다.

## 검토한 선택지

| 기준 | FastAPI | Django (+DRF/Ninja) | Litestar | Node (NestJS/Hono) |
|---|---|---|---|---|
| 워커와 스키마 공유 | Pydantic 그대로 공유 | 별도 직렬화 계층 필요(Ninja는 Pydantic) | msgspec/Pydantic 지원 | 불가 — 스키마 이중 정의 |
| 비동기·SSE | 네이티브 async, SSE 간단 | async 지원 있으나 ORM 등 일부 동기 | 네이티브 async | 강함 |
| 인증·관리자 화면 | 직접 구성 | 내장 admin·auth (큰 장점) | 직접 구성 | 직접 구성 |
| 생태계·채용 시장 인지도 | AI 백엔드 사실상 표준 | 높음(웹 일반) | 낮음 | 높음(웹 일반) |
| 1인 학습·유지 비용 | 낮음 | 중간(관례 많음) | 낮음, 자료 적음 | 언어 2개 유지 |
| OpenAPI 자동 생성 | O | Ninja로 O | O | 라이브러리 |

## 결정 (제안)
**FastAPI**. ORM은 SQLAlchemy 2.x + Alembic(작은 선택 → `tech-choices.md`).

## 이유
1. 워커(LangGraph)와 API가 **같은 Pydantic 스키마**를 쓰므로 `docs/schemas.md`를 한 번만 구현하면 된다.
2. SSE·비동기 작업 생성 같은 이 서비스의 API 형태에 맞다.
3. AI Engineer 직군 면접관에게 설명 비용이 가장 낮다.

## 결과·트레이드오프 (포기한 것)
- Django admin을 포기한다 → 내부 운영 화면(이의 제기 검토, 사용자 삭제 요청 처리)을 직접 만들어야 한다. M3에서 최소 기능(목록·상세·처리 버튼)만 만들고, 필요하면 SQL 콘솔로 대신한다.
- 인증을 직접 조립해야 한다 → 관리형 인증(소셜 로그인) 사용 여부는 M3에서 별도 결정.

## 재검토 조건
- 운영 화면 요구가 커져 직접 구현 비용이 1주 이상 들 때 → Django(+Ninja)로 운영 화면만 분리하는 안 검토.
