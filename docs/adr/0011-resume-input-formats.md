# ADR-0011: 이력서 입력 형식 (HWP·스캔 PDF 포함)

- 상태: 채택됨 (2026-11-01) — 지원 범위는 사용자 결정, 처리 방법은 M1 정확도 측정 후 재확인
- 날짜: 2026-11-01
- 관련: ADR-0004(격리 작업), `docs/design.md` §6, `docs/ethics/fairness-policy.md` §2

## 배경
한국 이력서는 HWP/HWPX와 스캔 PDF(글자가 아닌 이미지)가 흔하다. 사용자가 "둘 다 처리되게 하라"고 결정했다(Q11). 제약은 네 가지다.
- 비용 0원에 가깝게
- 이력서 사진이 LLM 제공자에게 가지 않게 (공정성 정책: 사진은 쓰지 않는다)
- 업로드 파일은 신뢰할 수 없는 입력이다
- 오픈소스 라이선스가 서비스 운영과 충돌하지 않게

## 지원 형식과 처리 경로

| 형식 | 처리 | 비고 |
|---|---|---|
| 텍스트 붙여넣기 | 그대로 | |
| 텍스트 PDF | PDF 텍스트 추출 | 페이지별 추출 텍스트가 거의 없으면 스캔 PDF로 판정해 OCR 경로로 |
| DOCX | XML 텍스트 추출 | |
| **HWPX** | ZIP 안의 XML(OWPML) 파싱 — 표준 라이브러리만 사용 | 의존성 없음 |
| **HWP 5.x** | OLE 복합 문서 → BodyText 섹션 압축 해제 → 문단 텍스트 레코드 추출 | 한컴이 공개한 HWP 5.0 형식 문서 기준으로 직접 구현 |
| **스캔 PDF / 이미지(JPG·PNG)** | 페이지 이미지 → **로컬 OCR** → 텍스트 | 이미지 자체는 LLM에 보내지 않음 |
| HWP 3.x 이하, 암호 걸린 파일 | 미지원 안내 | 드묾 |

## 결정 1: HWP 파서

| 기준 | pyhwp | syhwp | **직접 구현 (공개 형식 문서 기준, 텍스트만)** | LibreOffice + 변환 확장 |
|---|---|---|---|---|
| 라이선스 | **AGPL-3.0** — 서비스로 운영하면 소스 공개 의무 | MIT | 우리 저장소 라이선스 | MPL 등 |
| 성숙도 | 오래됨 | 신생(초기 버전) | 우리가 테스트로 보증 | 성숙 |
| 범위 | 넓음 | 텍스트 위주 | 텍스트만(표 안 텍스트 포함) | 레이아웃까지 |
| 무게 | 중간 | 가벼움 | 가벼움(olefile + zlib) | 무거움(컨테이너 수백 MB) |
| 비용 | 0 | 0 | 0 | 0, 단 실행 메모리↑ |

**결정**: 직접 구현한다. HWPX는 표준 라이브러리, HWP 5.x는 `olefile`(BSD) + `zlib`을 쓴다. syhwp는 테스트 시 출력 비교용 참고로만 쓴다.

이유:
- 우리에게 필요한 건 "텍스트"뿐이라 구현 범위가 작다.
- AGPL을 들이면 저장소 라이선스 선택이 강제된다.
- 신생 라이브러리에 핵심 입력을 맡기지 않는다.
- 면접에서 "공개 형식 문서를 읽고 파서를 구현했다"고 설명할 수 있다.

## 결정 2: OCR

| 기준 | **Tesseract (kor)** | **PaddleOCR** | LLM 비전 (Haiku 5.5) |
|---|---|---|---|
| 비용 | 0 (로컬) | 0 (로컬) | 페이지당 수천 토큰 — 저렴 |
| 사진·개인정보 | 로컬 처리 | 로컬 처리 | **페이지 이미지 전체(사진 포함)가 제공자에 전송됨** |
| 한국어 정확도 | 보통(추정) | 상대적으로 높음(추정) | 높음(추정) |
| 실행 자원 | 가벼움 | 무거움(모델 파일, 메모리) | 없음 |
| 라이선스 | Apache-2.0 | Apache-2.0 | — |

**결정**: 로컬 OCR을 쓰고 LLM 비전은 쓰지 않는다. Tesseract와 PaddleOCR 중 하나는 M1에서 합성 스캔 이력서(구성상 정답 텍스트가 있음)로 문자 오류율을 재서 고르고, 결과를 이 ADR에 기록한다.

이유: LLM 비전이 정확도는 가장 좋을 수 있다. 하지만 이력서 사진을 외부로 보내지 않는다는 공정성·개인정보 원칙이 우선이다. 사진 영역을 가리고 보내는 방법도 있지만, 가리는 단계가 실패하면 사진이 전송된다. 그래서 구조적으로 막는 쪽을 택한다.

## 결정 3: 안전한 처리
- 모든 파일 파싱·OCR은 ADR-0006의 격리 작업과 같은 방식(일회성 컨테이너, 네트워크 차단, 시간·메모리 상한)으로 실행한다.
- 업로드 검증: 확장자가 아니라 파일 시그니처(매직 바이트)로 형식을 판정한다. 크기 상한(예: 10MB)과 페이지 수 상한(예: 10쪽)을 둔다. 압축 해제 크기 상한으로 압축 폭탄을 막는다.
- 추출 직후 원본은 삭제한다(기본값). 이미지에서 사진 영역은 OCR 입력에서 제외하거나 무시한다. 추출 텍스트는 민감정보 제거 → PII 마스킹을 거친 뒤에만 LLM으로 간다(`design.md` §6).
- OCR 신뢰도가 낮은 줄은 fact 후보에 "확인 필요"로 표시해 사용자 확인 단계(Profile Builder interrupt)에서 바로잡게 한다.

## 결과·트레이드오프 (포기한 것)
- HWP 직접 구현은 형식의 예외 케이스(표 중첩, 각주, 특수 개체)에서 텍스트를 놓칠 수 있다. 합성 HWP/HWPX 테스트 파일로 회귀 테스트를 둔다.
- 로컬 OCR은 LLM 비전보다 정확도가 낮을 수 있다. 사용자 확인 단계가 그 오류를 흡수하는 구조다.
- M1 작업량이 늘어난다. Profile Builder는 텍스트 경로를 먼저 완성하고, 그다음 HWP → OCR 순으로 붙인다.

## 재검토 조건
- M1 측정에서 로컬 OCR의 문자 오류율이 너무 높아 사용자 확인 부담이 커질 때. 이때는 사진 영역 제거를 검증할 수 있는 경우에 한해 LLM 비전을 다시 검토한다.
- syhwp 등 허용적 라이선스 파서가 충분히 성숙하면 직접 구현을 대체할 수 있다.
