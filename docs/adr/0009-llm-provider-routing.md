# ADR-0009: LLM 제공자·모델 라우팅

- 상태: 채택됨 (2026-11-01)
- 날짜: 2026-11-01
- 관련: ADR-0002, ADR-0008, `docs/design.md` §5

## 배경
- 예산: 월 ₩10,000(약 $7). 인프라는 0원을 목표로 하므로 이 예산은 전부 LLM 몫이다.
- 사용자 상황: OpenAI 크레딧이 약 $4 남아 있다. Claude Max를 결제할 계획이다(약 7일 뒤). Max에는 매달 Claude API 크레딧이 포함된다. 이 크레딧은 Claude Code·Claude 앱에서는 쓸 수 없지만 API 호출에는 쓸 수 있다(공식 도움말 기준).
- 제공자를 바꾸면 출력 분포가 바뀌므로 기준선 측정과 녹화 응답을 다시 만들어야 한다. 그래서 **교체 비용을 설계로 낮춰야** 한다.
- 사용자가 TypeSafe의 Jev(2026-09-15 출시)를 라우팅 노드로 쓰자고 제안했다.

## 결정 1: 제공자 단계 (사용자 결정)
| 단계 | 기간 | 제공자·모델 | 비용 출처 |
|---|---|---|---|
| 1 | 지금 ~ Max 결제 | OpenAI 저가 모델 (가격표는 사용자 계정에서 확인 후 이 ADR에 기록) | 남은 크레딧 약 $4 |
| 2 | Max 결제 후 | **모든 노드 Claude Haiku 5.5** ($0.10 / $0.50 per MTok, 프롬프트 10만 토큰 이하 기준) | Max 포함 API 크레딧 |
| 3 | 평가로 필요가 입증될 때만 | Requirement Matcher만 Sonnet 5.5로 올리는 것을 검토 | 크레딧 한도 안에서 |

단계 2로 넘어갈 때 기준선을 다시 측정한다. **M1의 공식 기준선은 단계 2(Haiku 5.5)에서 확정**한다. 단계 1의 결과는 파이프라인이 끝까지 도는지 확인하는 용도로만 쓴다.

Haiku 5.5는 프롬프트가 10만 토큰을 넘으면 단가가 5배가 된다. 저장소당 토큰 상한(ADR-0006, 20k)과 요청 단위 토큰 상한으로 이 경계를 넘지 않게 한다.

## 결정 2: 교체 가능한 설계 (사용자 요구)
```
app/rigor/llm/
  client.py      # LLMClient 프로토콜: structured(task, messages, schema) -> (결과, Usage)
  adapters/      # openai.py, anthropic.py, fake.py (테스트), recorded.py (녹화 재생)
  routing.py     # task → (provider, model, params) 해석
configs/routing.yaml
```
- 노드는 모델 이름을 모른다. **역할(task)만 요청한다**: `jd_parse`, `fact_extract`, `repo_summarize`, `requirement_verdict`, `review_write`, `roadmap_write`, `claim_verify`, `policy_classify`, `judge`.
- `routing.yaml`이 task를 제공자·모델에 연결한다. 제공자 교체 = 설정 파일 변경 + `make rebaseline`(녹화 응답 재생성 + 평가 재실행 + 기준선 보고서 생성).
- 구조화 출력은 두 제공자의 차이를 어댑터에서 흡수한다. 노드에는 Pydantic 스키마만 보인다.
- 모든 결과의 `Provenance`에 provider·model·routing 설정 해시를 기록한다. 평가 보고서도 이 해시 단위로 나눠 저장한다.
- 녹화 응답은 (task, 입력 해시, routing 해시)로 저장한다. 해시가 바뀌면 녹화를 다시 해야 한다는 사실이 CI에서 드러난다.
- 토큰 단가는 `configs/pricing.yaml`에 확인 날짜와 함께 둔다. 원가 지표는 여기서 계산한다.

## 결정 3: Jev를 라우팅 노드로 쓰지 않는다

Jev가 무엇인가: 텍스트를 생성하지 않고 정해진 선택지 중 하나와 그 확률을 돌려주는 "System One" 모델이다. 출력 형태는 Choice, Score, Noul(예/아니오 확률) 세 가지다. 대표 용도가 "요청마다 어떤 모델을 쓸지 고르는 라우터"다.
- 공개된 수치: 입력 $0.042/MTok, 출력 무료, 컨텍스트 32k, 지연 70~500ms.
- 단, 모두 출시 시점의 회사 발표 수치이고 독립 검증은 아직 없다.

| 기준 | Jev를 모델 라우터로 사용 | **정적 라우팅 (task별 고정 모델)** |
|---|---|---|
| RIGOR에 라우팅할 대상이 있나 | 서브그래프 선택은 요청 종류(API 경로)로 이미 정해진다. 모델 선택만 남는데 단계 2에서는 모든 노드가 Haiku 5.5다 | 해당 없음 |
| 비용 절감 여지 | Haiku 5.5($0.10)보다 더 싼 쪽으로 보낼 후보가 거의 없다. 라우팅 호출 비용이 추가된다 | 0 |
| 판정 안정성·재현성 | 같은 입력이 요청마다 다른 모델로 갈 수 있다 → ADR-0008의 "같은 근거 → 같은 등급"을 깨기 쉽다 | 유지 |
| 평가 부담 | 라우터가 고를 수 있는 모든 모델 조합에 기준선이 필요하다 | 모델당 1회 |
| 개인정보 | 이력서 요약이 제3의 사업자(TypeSafe)에 추가로 전송된다 → 처리위탁·국외 이전 고지 대상이 늘어난다 | 제공자 1곳 |
| 성숙도 | 출시 약 7주. 대기자 등록 기반 접근, 공식 가격 페이지·요청 한도 미공개, 가격 보조금 여부 불명. 오픈소스 라우터들은 "실험적" 단계다 | — |
| 한국어 | 지원 여부 확인 못 함 | — |

**결론**: 지금 RIGOR에는 모델 라우터가 풀어 줄 문제가 없다. 오히려 판정 안정성과 평가 비용에서 손해다.

**대신 Jev가 맞을 수 있는 자리 (M2 실험 후보)**: Jev의 강점은 "정해진 선택지에서 고르기 + 확률"이다. RIGOR에도 그런 작업이 있다.
- README 섹션 분류 (문제 / 설계 / 실행법 / 결과)
- 공개 메타데이터만으로 하는 저장소–공고 관련성 1차 선별
- 프롬프트 인젝션 의심 문장 탐지

이 작업들은 **개인정보가 없는 공개 저장소 텍스트**만 다루므로 개인정보 문제가 없다. 위 `LLMClient`에 `classify` 작업 유형으로 붙일 수 있게 설계를 열어 두고, 아래 조건이 충족되면 Haiku 5.5와 비교 실험을 한다.
- 공식 가격·한도·데이터 정책이 공개될 것
- 한국어 README에서도 동작이 확인될 것
- 구성상 정답이 있는 합성 세트에서 정확도와 보정 품질(confidence 0.9가 실제로 90% 맞는지)을 측정할 수 있을 것

## 이유
- 예산 안에서 가장 싼 모델(Haiku 5.5)로 전 노드를 시작하면 모델 선택 자체가 단순해진다. 모델을 올리는 결정은 평가 근거가 생길 때만 한다.
- task 기반 라우팅 + 어댑터 + 녹화 해시 덕분에 제공자 교체가 "코드 수정"이 아니라 "설정 변경 + 재측정 명령"이 된다.

## 결과·트레이드오프 (포기한 것)
- 단계 1(OpenAI)에서 만든 프롬프트는 단계 2에서 다시 다듬어야 할 수 있다.
- 동적 라우팅으로 얻을 수 있는 약간의 비용·지연 이득을 포기한다.
- 평가 채점 모델(judge)도 Haiku 5.5다. 같은 모델이 출력과 채점을 함께 하면 편향 우려가 있다. 그래서 judge는 구성상 정답으로 정확도가 확인된 항목에만 쓴다(`metrics.md` §1.5).

## 재검토 조건
- Max 포함 API 크레딧 금액이 확인되어 월 사용량을 감당하지 못할 때.
- 평가에서 Haiku 5.5의 요건 판정 정확도가 기준에 못 미칠 때 → 단계 3.
- Jev의 공식 가격·데이터 정책이 공개되고 위 실험 조건이 충족될 때.

## 승인 기록 (2026-11-01)
- 승인: `flashattention`. 제공자 단계 계획과 교체 가능한 설계는 사용자가 직접 정했다. Jev 미채택은 조사 결과(라우팅 대상 없음, 판정 안정성·평가 부담·개인정보 손해, 초기 단계)에 따른 판단을 사용자가 승인했다.
