# ADR-0010: 벡터 DB·RAG 도입 범위

- 상태: 제안됨
- 날짜: 2026-11-01
- 관련: ADR-0004(Postgres+pgvector), ADR-0006, `docs/design.md` §3

## 배경
사용자 질문: RIGOR에 벡터 DB나 RAG가 들어갈 여지가 있는가.

판단 기준은 두 가지다.
- **실제로 검색이 필요한 문제가 있는가.** 검색 대상이 크고, 무엇이 필요한지 미리 알 수 없을 때만 검색이 필요하다.
- **포트폴리오용으로 끼워 넣는 것이 아닌가.** RIGOR가 사용자에게 "근거 없는 프로젝트를 이력서에 쓰지 마라"고 말하는 서비스이므로, RIGOR 자신도 필요 없는 기술을 넣으면 안 된다.

## 후보 지점 분석

| 지점 | 검색 대상 규모 | 필요성 | 판단 |
|---|---|---|---|
| Requirement Matcher: 요건 ↔ 프로필 fact 연결 | fact 20~80개, 수천 토큰 | 통째로 프롬프트에 넣을 수 있다. 검색 단계를 넣으면 놓치는 근거(검색 실패)만 생긴다 | **불필요** |
| Requirement Matcher: 요건 ↔ 저장소 근거 연결 | 저장소 결정론 신호 + 발췌, 저장소당 상한 20k 토큰 | 작은 저장소는 통째로 가능하다. 큰 저장소에서는 "이력서 주장과 관련된 파일 찾기"가 실제 검색 문제다 | **필요 — 단, 요청 단위 일회성 검색** |
| Repo Auditor: 큰 저장소의 관련 파일 선택 | 파일 수백~수천 개 | 같음. 첫 수단은 결정론(의존성 파일, import 문, 경로·파일명 키워드)이고, 그다음이 BM25 같은 어휘 검색이다 | **어휘 검색 우선, 임베딩은 실험으로** |
| 기술명 정규화 (taxonomy) | 기술 수백 개 | 별칭 표로 대부분 해결된다. 표에 없는 기술만 유사도 후보를 사람(개발자)이 검토해 표에 추가한다 | 메모리 내 처리, DB 불필요 |
| 매칭 (M4): 프로필 → 후보 공고 검색 | 공고 수천 건 이상(수집 출처에 따라 다름) | 진짜 대규모 검색 문제다. 브리프 원안의 Candidate Retrieval | **pgvector 하이브리드 검색 — M4** |
| 채용 가이드 같은 외부 지식 RAG | — | 진단 근거는 공고·fact·저장소만이어야 한다. 외부 문서를 섞으면 근거 없는 일반론이 들어온다 | **도입하지 않음** |

## 결정 (제안)
1. **M1~M3: 상시 벡터 DB를 쓰지 않는다.** 코어 흐름의 근거 연결은 "전부 넣기"(fact) + "결정론 → 어휘 검색"(큰 저장소)으로 한다.
2. **큰 저장소의 근거 검색은 요청 단위·일회성**이다. 분석이 끝나면 인덱스를 버린다. 저장소 코드를 분석 후 삭제한다는 원칙(브리프 §5.4)과 맞추기 위해서다. 영구 저장소에 코드 임베딩을 남기지 않는다.
3. **M2 실험**: 합성 저장소에 "이력서 주장의 근거 파일"을 심고 근거 검색 recall@k를 측정한다.
   - 비교 대상: ① 결정론만 ② +BM25 ③ +임베딩 하이브리드
   - 임베딩은 ②보다 recall이 의미 있게 오르고 비용이 예산 안일 때만 채택한다.
4. **M4 매칭**: 이미 쓰는 Postgres의 pgvector로 하이브리드 검색(어휘 + 임베딩 + 직무 분류 필터 + 결격 조건 하드 필터)을 한다. 별도 벡터 DB 서비스를 두지 않는다. 추가 인프라 비용은 0원이다.

## 이유
- 검색 단계는 "놓친 근거"라는 새로운 실패 유형을 만든다. 넣을 수 있는 양이면 넣는 것이 정확하고, 결과를 설명하기도 쉽다.
- 근거 검색은 실제로 필요한 곳(큰 저장소, M4 매칭)에만 두고, **비교 실험으로 효과를 측정해 채택한다.** 그러면 포트폴리오에서 "RAG를 썼다"가 아니라 "검색이 필요한 곳을 판별하고, 방식별 recall을 측정해서 골랐다"를 보여 줄 수 있다. Agent Engineer 직군 공고가 요구하는 검색 역량(taxonomy C03)과 평가 역량(C04)을 함께 증명하는 방식이다.
- 별도 벡터 DB SaaS를 쓰지 않으므로 비용 원칙과도 맞다.

## 결과·트레이드오프 (포기한 것)
- M3까지 "벡터 DB 운영 경험"은 생기지 않는다. 대신 검색 품질 평가(recall@k 비교) 경험이 생긴다.
- 큰 저장소에서 어휘 검색이 표현이 다른 근거(예: 이력서는 "캐싱", 코드는 `memoize`)를 놓칠 수 있다. M2 실험이 이 위험을 측정한다.

## 재검토 조건
- M2 실험에서 임베딩 하이브리드의 recall 이득이 크면 M2부터 채택한다.
- 프로필 fact가 프롬프트에 다 들어가지 않을 만큼 커지면(예: 수백 개) fact 검색 도입을 검토한다.
