# ADR-0006: GitHub 분석 방식 (API vs clone, 격리, 인증, 캐시)

- 상태: 채택됨 (2026-11-01)
- 날짜: 2026-11-01
- 관련: ADR-0004, `docs/design.md` §2.2·§3·§7, `docs/rubric.md` §4

## 배경
Repo Auditor는 핵심 흐름의 절반이다. 요구: 이력서 ↔ 저장소 사실 대조, 본인 기여 통계, 품질 루브릭, 노출 위험 점검. 제약: ① 코드는 **신뢰할 수 없는 입력** ② 저장소당 LLM 토큰 비용이 크다 ③ **최소 권한·본인 계정만** ④ GitHub API 요청 한도.

## 결정 1: 수집 방식

| 기준 | API만 | 항상 clone | **하이브리드 (API 우선 + 조건부 격리 clone)** |
|---|---|---|---|
| 보안 표면 | 최소(HTTP JSON만) | clone 단계 취약점, 자원 고갈 | clone 시에만, 격리 작업 안에서 |
| 커버리지 | README·트리·특정 파일·커밋 목록·작성자별 통계 | 전체 파일, blame, 전수 비밀값 스캔 | 둘 다 |
| 비용 | API 요청 수(한도) | 컴퓨트·디스크 | 필요한 저장소만 컴퓨트 |
| 지연 | 저장소당 수 초 | 수 초~수십 초 | 대부분 API 속도 |

**결정**: 하이브리드. clone은 ① 비밀값 전수 스캔 ② 줄 단위 기여(blame)가 필요할 때 ③ API 크기 확인 결과 상한 이하일 때만.

## 결정 2: 인증

| 기준 | 인증 없음(공개만) | OAuth App | **GitHub App** |
|---|---|---|---|
| 비공개 저장소 읽기 전용 | 불가 | **불가** — `repo` scope는 모든 비공개 저장소의 읽기·쓰기 | Contents: read, Metadata: read |
| 저장소 단위 선택 | — | 불가(전체) | **설치 시 저장소 선택** |
| 본인 확인 | 불가 | O | O(사용자 토큰) |
| 토큰 수명 | — | 장기 | 사용자 토큰 만료·갱신 구조 |
| 요청 한도 | 매우 낮음 | 사용자 단위 | 설치·사용자 단위 |

**결정**: M1은 공개 저장소를 개발자 개인 토큰 또는 인증 없이(CLI, 본인 저장소만). M2부터 **GitHub App**. 분석 대상은 "인증된 사용자가 소유한 저장소 + 사용자가 기여자인 저장소 중 사용자가 선택한 것"으로 제한한다(팀 저장소의 기여 분석은 사용자 본인 커밋 통계만 표시).

## 결정 3: 격리 실행 (clone 작업)
- 실행 위치: 요청 단위 일회성 작업(ADR-0004의 Cloud Run Jobs), 전용 서비스 계정(DB의 결과 테이블 쓰기 권한만).
- git 설정: 패치된 git 버전 고정, `--depth` 제한, `--filter=blob:limit=1m`, `--no-recurse-submodules`, `core.hooksPath=/dev/null`, `GIT_LFS_SKIP_SMUDGE=1`, `protocol.file.allow=never`, 필터·smudge 드라이버 비활성화, `core.symlinks=false`.
- 상한: 저장소 크기(API 기준) N MB 초과 시 clone 생략, 파일 수·디스크·메모리·실행 시간 상한.
- 네트워크: 송신은 github.com만. 루트 파일시스템 읽기 전용, 작업 디렉터리만 쓰기, 비root.
- 수명: 작업 종료 시 컨테이너와 함께 삭제. 결과(구조화 신호)만 DB에 기록, 코드 본문은 저장하지 않음.
- **어떤 코드도 실행하지 않는다**: 빌드·설치·테스트 실행·노트북 실행 금지. 정적 파서와 스캐너만.

## 결정 4: 토큰 상한과 계층 요약
1. 1차(메타데이터만): 이름·설명·주제·언어·크기·포크 여부·최근 커밋 → 공고 관련성 선별. 관련 없는 저장소는 결정론 신호만 표시하고 LLM 심층 분석 생략.
2. 2차(결정론): README 헤딩 구조, 파일 트리 요약(디렉터리별 파일 수), 매니페스트, CI·테스트·라이선스 존재, 커밋 통계.
3. 3차(LLM, 상한 내): README 본문 + 이력서 claim과 관련된 파일 발췌만. 저장소당 입력 토큰 상한(초기값 20k, M1 실측 후 조정).

## 결정 5: 캐시
- 키: `(repo_id, head_commit_sha, analyzer_version, rubric_version)`. 결정론 신호와 LLM 해석을 분리 저장해, 루브릭만 바뀌면 신호는 재사용.
- 공고 관련성 판정은 공고 의존이므로 캐시하지 않거나 `(repo 캐시 키, jd_hash)`로 별도 캐시.
- 보존: 90일 또는 연결 해제·계정 삭제 시 즉시 삭제. 비공개 저장소 캐시는 암호화.

## 이유
- 보안 표면과 비용을 함께 줄이는 유일한 방법은 **필요할 때만 clone하고, LLM에는 발췌만 넣는 것**이다.
- GitHub App만이 브리프의 최소 권한·저장소 단위 선택 요구를 실제로 충족한다.

## 결과·트레이드오프 (포기한 것)
- 대부분의 저장소에서 blame 기반 줄 단위 기여는 제공하지 않는다(커밋 통계로 대체). 기여 표시는 원래 "판정 아님"이므로 수용 가능.
- GitHub App은 등록·설치 흐름이 OAuth보다 복잡하다(M2에 반나절~1일 추가).
- 비밀값 스캔은 clone하지 않은 저장소에서 API로 가져온 파일 범위로 제한된다 → 리포트에 "스캔 범위"를 명시.

## 재검토 조건
- clone 작업의 실패율·비용이 기준을 넘을 때 → API 전용으로 축소.
- GitHub 권한 모델 변경 시.

## 승인 기록 (2026-11-01)
- 승인: `flashattention`. GitHub App만이 최소 권한·저장소 단위 선택을 충족하고, 하이브리드 분석이 보안 표면과 비용을 함께 줄인다는 이유로 채택.
- **비용 관점**: GitHub API·GitHub App은 무료. clone 작업은 Cloud Run Jobs 무료 사용량 안에서. 비용의 대부분은 감사의 LLM 입력 토큰이므로 ① 관련 저장소만 심층 분석 ② 결정론 신호 우선 ③ 커밋 해시 캐시 ④ 저장소당 토큰 상한을 **예산 장치**로도 본다.
