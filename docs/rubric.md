# 진단 루브릭 (M0 초안 v0.1)

> M1에서 `configs/rubric.yaml`, `configs/grading.yaml`로 옮긴다. 수치 기준마다 근거를 §2에 적었다. 근거가 약한 값은 잠정값으로 표시하고, 베타 사용자 결과 데이터로 다시 보정한다.
> 범위: ① 요건 판정 ② 등급 규칙 ③ 서류 약점·갭 분류 ④ 저장소 품질·판정 ⑤ 어조 가이드.

---

## 1. 요건 판정 (RequirementVerdict)

| status | 기준 |
|---|---|
| `met` | `confirmed` fact 또는 저장소 근거가 요건을 직접 뒷받침하고, 근거 깊이 ≥ 요건 깊이 |
| `partial` | 관련 근거는 있으나 깊이가 1 부족, 또는 범위 일부만 충족 (예: "Kubernetes 운영" 요건에 Docker 배포만) |
| `unmet` | 관련 근거 없음, 또는 깊이가 2 이상 부족 |
| `unknown` | 판단에 필요한 정보가 프로필에 없음 → **질문 생성**, 등급 계산에서는 `unmet`으로 보되 리포트에 "확인 필요"로 별도 표시 |

필수 규칙:
- 근거는 `confirmed` fact와 저장소 근거만. `unconfirmed` fact는 인용 불가.
- 키워드 일치만으로 `met` 금지(키워드 스터핑 방어): 기술 목록(깊이 0)만 있으면 최대 `partial`이 아니라 **`unmet`** (요건 기본 깊이 2 대비 2 부족).
- 팀 성과(`attribution=team`)는 본인 역할이 명시된 경우에만 근거로 인정.
- `legal_check=flag` 요건(보호 속성 기반)은 판정하지 않는다.

## 2. 등급 규칙 (결정론)

정의: `R` = required 요건 수, `met=1, partial=0.5, unmet/unknown=0` 가중 충족률 `cov_req`, preferred 요건의 같은 값 `cov_pref`. `critical_gaps` = 핵심(●●) 역량에 연결된 required 요건 중 `unmet` 수.

평가 순서(먼저 맞는 규칙 적용):

| 규칙 id | 조건 | 등급 | 근거 |
|---|---|---|---|
| G1 | knockout 요건 중 `unmet`이 1개 이상 (확인된 미충족만; `unknown`이면 G1 대신 질문) | `not_recommended` | [B1] 정의 |
| G2 | `cov_req < 0.4` | `not_recommended` | [B2] 하한 |
| G3 | `critical_gaps ≥ 1` | `gap_first` | [B2] 단서 |
| G4 | `cov_req < 0.6` | `gap_first` | [B2] 상한 |
| G5 | 모든 required가 `met` 또는 `partial`이고, 핵심(●●) 역량에 연결된 required는 모두 `met`이고, 그 요건에 연결된 `showcase` 저장소 ≥ 1 | `strong` | [B1] 정의 |
| G6 | 그 외 | `apply` | — |

#### 기준의 근거
- **[B1] 정의에서 나온 규칙 (숫자 없음)**
  - knockout은 "충족하지 않으면 서류 단계에서 제외된다"고 공고가 명시한 조건이다. 그래서 knockout `unmet`은 곧 비추천이다. knockout 종류는 이진 판정이 가능한 것으로 한정한다: 학위, 자격증, 근무 자격(비자), 근무지.
  - 강력 추천은 비율이 아니라 "필수 요건에 빈칸이 없고, 핵심 요건은 근거가 완전하며, 그걸 보여 줄 저장소가 있다"는 정의로 정한다. 임의의 비율 기준(예: 0.9)을 두지 않는다.
- **[B2] 외부 근거에서 나온 숫자 (0.4, 0.6)**
  - TalentWorks가 자사 사용자 지원서 6,000건 이상을 분석한 결과(2018년 보도)가 근거다. 공고 요건을 40~50% 충족한 지원자의 면접 확률이 그보다 덜 충족한 지원자보다 크게 높았고(+85%), 60%를 넘으면 더 충족해도 면접률이 더 오르지 않았다. 단서: 핵심 하드 스킬이 빠지면 다른 요건 충족으로 만회되기 어렵다.
  - 이를 그대로 옮긴다. 40% 미만은 면접 가능성이 뚜렷이 낮은 구간이라 비추천(G2)이다. 40~60%는 가능성이 오르는 구간이라 갭 보완 후(G4)다. 60% 이상은 면접률이 더 오르지 않는 구간이라 지원 가능(G6)이다. 핵심 스킬 단서는 G3(치명적 갭 1개 이상이면 갭 보완 후)으로 반영한다.
  - **근거의 한계 (README에도 공개)**: 동료 평가를 거친 연구가 아니다. 미국의 전 직군 데이터이고 2018년 자료다. "요건 충족률"을 사람이 센 방식이 RIGOR의 `cov_req`와 다르다. 요건 충족률과 면접률의 관계를 직접 검증한 동료 평가 연구는 찾지 못했다(2026-11 조사 기준). 그래서 이 숫자는 **잠정값**이다. 베타 사용자 결과 데이터가 쌓이면 다시 보정한다(`metrics.md` §2.3).
- **[B3] 오류 비용의 비대칭 (판단이 애매할 때의 원칙)**
  - 잘못된 "비추천"은 사용자가 붙을 수 있었던 기회를 포기하게 만든다. 잘못된 "지원 가능"은 지원서 작성 시간 몇 시간을 쓰게 만든다. 앞의 비용이 더 크다.
  - 그래서 경계가 애매하면 덜 배제하는 쪽을 고른다. 연차 미달을 knockout으로 보지 않는 것(아래)과, `unknown`을 knockout 판정에 쓰지 않고 질문으로 돌리는 것이 이 원칙에서 나온다.
- **[관례] `partial` = 0.5**: 외부 근거가 없다. 불확실성 아래에서 중간값을 쓰는 관례다. 합성 평가셋에서 0.3~0.7로 바꿔 보며 등급이 얼마나 달라지는지 민감도 분석을 하고, 결과를 이 문서에 기록한다.

- `experience_years`: knockout으로 다루지 않는다([B3]). 공고가 연차를 필수로 명시했는데 확인된 경력이 모자라면, required 요건으로서 경력 비율만큼 `partial`(최소치의 50% 이상) 또는 `unmet`(50% 미만)으로 판정한다. 이 50%는 `partial`/`unmet` 경계를 정하는 관례값이고, 등급에는 `cov_req`를 거쳐서만 영향을 준다.
- 등급과 함께 `grade_trace`(규칙 id, 수치)를 리포트에 노출한다 → 사용자는 "무엇이 바뀌면 등급이 오르는지" 알 수 있다.
- **아첨 방어**: 등급은 verdicts의 함수다. 사용자가 압박해도 새 근거(fact 추가·확인, 저장소 변경)가 없으면 같은 입력 → 같은 등급. 테스트: 동일 verdicts + 압박 대화 → 등급 불변.

## 3. 서류 약점과 갭

### 3.1 서류 약점 카테고리 (weaknesses)
| id | 약점 | 탐지 근거 |
|---|---|---|
| W1 | 성과 수치 부재 | 프로젝트·경력 fact에 `metrics` 없음 |
| W2 | 근거 없는 수치 | `metrics` 있으나 `evidence_url` 없음 또는 ClaimCheck `not_found` |
| W3 | 역할 모호 | `attribution=team`인데 `role`·`contribution_note` 없음 |
| W4 | 직무 무관 경력 과다 | 목표 직무 핵심 역량에 연결되지 않는 fact 비중 > 50% |
| W5 | 이력서–저장소 불일치 | ClaimCheck `contradicted` 또는 기술 스택 `not_found` |
| W6 | 대표 프로젝트 부재 | 공고 관련 `showcase` 저장소 0개 |
| W7 | 최근성 부족 | 핵심 역량 근거가 모두 2년 이상 전 (관례값, 외부 근거 없음 — 등급에는 영향 없이 약점 안내에만 사용) |

### 3.2 갭 분류 (Gap.type)
| type | 정의 | 출력 |
|---|---|---|
| (a) expression | 근거 fact·저장소는 있는데 이력서에 드러나지 않음 | 이력서 수정 제안(부가 기능) |
| (b) missing_fact | 근거 자체가 없음 | 로드맵 항목(신규/보강 프로젝트) — **이력서 문장으로 메우지 않는다** |
| (c) knockout | 결격 | 비추천 + 대안 경로 |

심각도: critical = 핵심 역량 required / major = 기타 required / minor = preferred.

### 3.3 방향 전환 제안
조건: 지원자 근거의 역량 프로파일이 공고 직무보다 다른 직무(taxonomy §2)와 코사인 유사도가 일정 이상 높을 때(임계값 M1 튜닝). 예: 근거 대부분이 C07 → "이 공고(Agent Engineer)보다 Data Engineer 공고에 근거가 강하다". 반드시 근거 fact 인용.

## 4. 저장소 품질 루브릭

| id | 항목 | 측정(결정론 우선) | 점수 |
|---|---|---|---|
| Q1 | README: 문제 정의 | 섹션 분류 | 0–2 |
| Q2 | README: 설계·아키텍처 | 섹션·다이어그램 | 0–2 |
| Q3 | README: 실행법 | 설치·실행 명령 존재 | 0–2 |
| Q4 | README: 결과·평가 | 결과 표·지표·스크린샷 | 0–2 |
| Q5 | 테스트 | 존재 0 / 존재 1 / 핵심 모듈 커버 2 (파일 매핑 기반 근사) | 0–2 |
| Q6 | CI | 워크플로 존재·테스트 실행 단계 | 0–2 |
| Q7 | 배포·데모 | 배포 설정 또는 homepage URL (**URL 동작 확인은 HEAD 요청만**, M2) | 0–2 |
| Q8 | 코드 구조 | 모듈 분리·설정 분리·노트북 단독 여부 | 0–2 |
| Q9 | 커밋 습관 | 활동 주 수, 메시지 품질(일괄 업로드 1커밋 여부) | 0–2 |
| Q10 | 실험·평가 근거 | 평가 스크립트·결과 파일 | 0–2 |
| Q11 | 라이선스 | 존재 여부 | 0–1 |
| X1 | 비밀값 노출 | 스캐너 | **차단 항목**: 발견 시 판정과 무관하게 최우선 경고 |
| X2 | 실명·학교·연락처 노출 (블라인드 공고) | 프로필 대조 | 블라인드 공고면 차단 항목 |
| X3 | 포크·무변경 | is_fork + 사용자 커밋 0 | → `drop` |
| X4 | 튜토리얼 복제 | 원본 튜토리얼과 유사 구조 + 사용자 고유 변경 적음 (휴리스틱, 신뢰도 표시) | → 최대 `improve` |

### 4.1 저장소 판정 (공고 기준, 규칙)
- `relevance` = 저장소 근거가 연결된 공고 required 요건 수(0이면 무관).
- `quality` = Q1–Q11 합 / 만점.

| 조건 | 판정 |
|---|---|
| X3, 또는 `relevance=0`이고 `quality < 0.3` | `drop` |
| `relevance ≥ 1` 그리고 `quality ≥ 0.65` 그리고 X1·X2 없음 | `showcase` |
| `relevance ≥ 1` (그 외) | `improve` + 부족 항목을 Improvement로 |
| `relevance=0`이고 `quality ≥ 0.3` | `drop` (이 공고에는 공간 낭비) — 단, "다른 직무엔 유용" 메모 |

### 4.2 기여·AI 도구 표시 원칙
- 커밋 비중은 판정 입력이 아니다. "면접에서 담당 영역을 설명할 준비" 안내로만.
- AI 도구 사용은 **탐지하지 않는다.** 사용자가 `implementation=mostly_ai`로 신고하면 "설계 결정과 검증 방법을 설명할 수 있게 ADR·테스트를 남겨라"는 보완 항목을 추천할 수 있다.

## 5. 어조 가이드

| 원칙 | 하라 | 하지 마라 |
|---|---|---|
| 대상 | 문서·요건·저장소에 대해 말한다 | 사람의 능력·성격·배경을 평가 |
| 직설 | "필수 요건 r_3(Kubernetes 운영) 근거가 없다" | "아마 괜찮을 것 같다", 근거 없는 위로 |
| 근거 | 모든 문장에 인용 | "일반적으로 회사들은..." 같은 근거 없는 일반화 |
| 비추천 | 이유 + 대안 경로 1개 이상 | 대안 없는 거절 |
| 강도 선택 | `gentle`은 표현·순서만 부드럽게 | `gentle`에서 등급·갭을 숨기거나 낮춤 |
| 금지 | — | 보호 속성 언급, "비전공자라서", "나이가", 학교 언급, 비하·조롱 |
| 위조 요청 | 거절 + 이유 + 사실 기반 대안 | 수치·경험 생성 |
| 고통 신호 | 판정을 반복해 밀어붙이지 않고, 선택적으로 지원 정보 안내 | 진단 거부, 과잉 개입 |
