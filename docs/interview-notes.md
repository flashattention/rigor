# 면접 노트

> 핵심 로직·설계 결정마다 짧은 설명, 예상 질문 3개, 직접 해 볼 연습 과제 1개를 남긴다. 답변 초안은 일부러 비워 둔다 — 직접 써 보는 것이 연습이다.

## M0-1. 등급을 LLM이 아니라 규칙으로 계산한다 (ADR-0008)
**설명**: LLM은 공고 요건마다 met / partial / unmet / unknown만 판정한다. 등급은 그 판정에서 규칙이 계산한다. 그래서 같은 근거에서는 항상 같은 등급이 나온다.
- 사용자가 압박해도 새 근거가 없으면 등급이 바뀌지 않는다(아첨 방어).
- 기준값마다 근거가 있다: 정의, 외부 자료, 오류 비용 비대칭.

**예상 질문**
1. LLM이 요건 판정을 실행마다 다르게 내면, 규칙으로 계산해도 결국 등급이 흔들리지 않나요? 그 흔들림을 어떻게 측정하나요?
2. 40% / 60% 기준의 근거가 동료 평가를 거친 연구가 아닌데, 왜 그 숫자를 썼나요? 틀렸다는 걸 어떻게 알게 되나요?
3. 연차 미달을 결격으로 보지 않는 이유는? 그 결정이 틀리면 사용자에게 어떤 비용이 생기나요?

**연습 과제**: `partial`의 가중치를 0.3~0.7로 바꿨을 때 등급이 바뀌는 합성 케이스 비율을 계산하는 민감도 분석을 설계해 보세요. 어떤 케이스를 만들어야 경계 효과가 드러날지 먼저 손으로 3개 적어 보세요.

## M0-2. 사람 라벨 없이 평가한다 (`metrics.md` §0)
**설명**: 외부 라벨러를 쓰지 않는다. 정답을 먼저 정하고 템플릿 코드로 데이터를 생성한다(구성상 정답). 예를 들어 "요건 3은 미충족", "이 저장소엔 LangGraph가 없다"를 설계한 뒤 그에 맞게 만든다.
- 아첨·인젝션·공정성은 "바뀌면 안 된다"를 확인하는 테스트라 라벨이 필요 없다.
- 주관적 타당성은 실사용자 피드백 전까지 미검증으로 공개한다.

**예상 질문**
1. 합성 데이터를 만드는 사람과 평가받는 시스템이 같은 가정을 공유하면 평가가 부풀려지지 않나요? 어떻게 완화했나요?
2. "현직자 눈에 맞는 진단인가"를 측정하지 못한다면, 이 시스템이 유용하다는 걸 어떻게 주장하나요?
3. LLM-as-judge를 왜 제한적으로만 쓰나요?

**연습 과제**: 이력서–저장소 불일치를 심은 합성 쌍 3개를 직접 설계해 보세요(기술 스택 불일치, 근거 없는 수치, 기여 과장 각 1개). 각 쌍의 "정답 판정"과 "에이전트가 헷갈릴 만한 지점"을 적어 보세요.

## M0-3. 사실을 먼저 맞추고 판단한다 (ADR-0017)
**설명**: 이력서 claim을 저장소·커밋과 대조하고, 불일치는 사용자가 고르게 한 뒤(interrupt), 정합된 프로필로만 공고 적합도를 판단한다.
- tool calling은 "근거 파일 찾기" 한 곳에만 쓴다. 경로를 미리 알 수 없기 때문이다.
- 나머지는 코드가 흐름을 정하는 워크플로다.

**예상 질문**
1. 워크플로와 에이전트(tool calling)를 어떤 기준으로 나눴나요? 반대로 했다면 무엇이 나빠지나요?
2. 커밋 수로 기여를 판단하면 생기는 문제는? (squash merge, 페어 프로그래밍, 다른 이메일)
3. 사용자가 "그대로 두기"를 고르면 시스템은 어떻게 동작하나요? 왜 막지 않았나요?

**연습 과제**: 커밋 작성자 이메일이 2개(회사 PC, 개인 PC)인 사용자의 합성 저장소를 상상해서, 별칭 확인 단계가 없을 때 `user_share`가 얼마나 틀어지는지 예시 숫자로 계산해 보세요.

## M1a-0. LLM 호출부: task 라우팅과 실패 처리 (`app/rigor/llm/`)
**설명**: 노드는 `client.structured(task, schema=...)`만 호출한다. 어떤 제공자·모델을 쓸지는 `configs/routing.yaml`이 정한다. 클라이언트가 한 곳에서 처리하는 것은 다음과 같다.
- **일시 오류**(요청 한도, 5xx, 타임아웃): 지수 백오프 + 지터로 재시도
- **영구 오류**(인증 등): 재시도 없이 바로 실패
- **스키마 검증 실패**: 오류 내용을 붙여 1회 재요청
- **비용**: 모든 호출을 task별로 누적하고, 예산을 넘으면 *다음 호출 전에* 멈춤
- 녹화 키는 (task, 모델, 프롬프트, 입력, 스키마, 파라미터)의 해시다. 무엇이든 바뀌면 재생이 실패하므로, "다시 녹화하고 재측정해야 한다"는 사실이 CI에서 드러난다.

**예상 질문**
1. 재시도를 SDK 내장 기능이 아니라 직접 구현한 이유는? (힌트: 재시도 횟수·비용 계측·테스트 가능성을 한 곳에서)
2. 스키마 검증 실패 시 무한 재요청을 하지 않는 이유와, 그래도 실패하면 사용자에게 무엇을 보여 주나?
3. 제공자를 OpenAI에서 Anthropic으로 바꿀 때 코드에서 바뀌는 곳과 바뀌지 않는 곳은?

**연습 과제**: `LLMClient._complete_with_retry`에 "같은 요청에서 누적 대기 시간이 30초를 넘으면 포기" 조건을 추가하고, `FakeAdapter` 큐로 테스트를 작성해 보세요.

## M1a-1. 합성 데이터 생성기: 구성상 정답 (`app/rigor/synth/`)
**설명**: 정답(요건 판정, 등급, claim 결과, 미연결 항목의 정답 저장소, 심은 노출, 기여 비율)을 먼저 정한다. 그다음 그 정답대로 이력서·공고 텍스트와 **실제 git 저장소**(작성자·이메일·날짜·AI 공동 작성 트레일러까지)를 만든다.
- 기본 케이스 5개 × 변형(반사실 8개, 인젝션 4개) = **65케이스**
- **자기 검증기**(`validate.py`)가 "정답과 데이터가 정말 일치하는지"를 코드로 확인한다. 예: "기술 claim이 supported면 그 의존성이 저장소에 있어야 한다", "기여 비율 정답 = 커밋 명세에서 계산한 값"
- 실제로 검증기가 내 변형 생성기의 버그 2개를 잡았다.
  - 인젝션 변형이 커밋을 하나 추가해 기여 비율이 바뀌던 문제
  - 반사실 변형이 이름을 바꿨는데 저장소 README에 옛 이름이 남아 노출 정답이 깨지던 문제

**예상 질문**
1. 정답을 만든 사람(당신)과 평가받는 시스템이 같은 가정을 공유하면 평가가 부풀려지지 않나요? 이 생성기는 그걸 어떻게 완화하나요?
2. 생성기 자체가 틀리면 어떻게 아나요? 자기 검증기가 잡지 못하는 종류의 오류는 무엇인가요?
3. 반사실 테스트에서 실명 학교와 가상 학교를 섞은 이유는? 둘 다 가상 이름이면 무엇을 측정할 수 없나요?

**연습 과제**: "포크만 하고 수정하지 않은 저장소" 케이스를 하나 추가해 보세요. `RepoSpec(is_fork=True)`, 사용자 커밋 0개로 만들고, 정답(`verdict=drop`)과 검증기 규칙("포크 + 사용자 커밋 0이면 drop이어야 한다")을 함께 추가해야 합니다.
